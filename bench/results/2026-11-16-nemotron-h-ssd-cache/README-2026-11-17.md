## A new conversation replaces one the SSD does not hold yet (`ab_nohit.py`)

`--slots 1`, default flags, a fresh empty `KAPITSA_HOME` per arm, main first, three pairs. A warm-up, request 1 (16K
tokens of the corpus, 64 greedy tokens), 3 s idle (the write-behind waits 10 s), request 2 (another conversation of
2.4K tokens, 64 tokens) with no warm-up: it takes the slot, so the branch copies request 1's conversation in memory
(`disk_leaving`: under the 512 MiB copied at once on 16 GB) and writes it in the background. Request 2:

| | First token, main | First token, branch | Last token, main | Last token, branch |
| --- | ---: | ---: | ---: | ---: |
| 4B, M4, rounds 1 / 2 / 3 | 5.004 / 5.017 / 5.012 s | 5.059 / 5.065 / 5.059 s | 7.629 / 7.596 / 7.599 s | 7.642 / 7.645 / 7.646 s |
| 9B v2, M2 | 15.900 / 15.874 / 15.870 s | 18.792 / 18.373 / 18.256 s | 20.690 / 20.710 / 20.829 s | 23.588 / 23.185 / 23.101 s |

- Where the branch's time goes (its server's `chat:` line): the copy shows as the `template/tokenize` time, 80-82 ms
  on the 4B (5 ms on main) and 1,657 / 566 / 163 ms on the 9B (17-23 ms on main). The write, 361 MB in 199-201 ms on
  the 4B and 422 MB in 1,514-1,893 ms on the 9B, runs during request 2's prefill: on the M2 the prefill's host
  encoding ends 1.3-2.2 s later than on main (`encoded by` 9,195 / 9,871 / 10,157 ms against 7,925 / 7,920 / 7,912
  ms); on the M4 it does not (2,467-2,474 against 2,491-2,503 ms).
- Request 1 (16,810 and 16,808 tokens) took the same in both arms (38.887-38.935 s on the 4B, 117.930-118.121 s on the
  9B), decode speed too, and both arms wrote the same text in every round.
- Load: no swap-outs. On the M2 `audiomxd` held 76% of a CPU core and `configd` 37-39% (`swap.log`).

## Logits through a restore (`trace_ttft.py`)

`tests/test_disk_cache.py --ttft --tokens 16000 --rounds 1` with `NI_TRACE_TOKENS` set for each server it starts
(`trace/server-NN.jsonl`, in start order: turn 1 with the cache; turn 2 from the SSD after a restart; without the
cache, turn 2 cold, turn 1, turn 2 from RAM). A line holds the request's first token, then every later token and the
top-1 minus top-2 logit margin of the row that chose it. Upstream, the Nano's two decode loops (prompt lookup on the 4B,
plain steps on the 9B) wrote no margins; `trace-instrument.patch` adds the two calls (plain steps then wait for each
step before queuing the next, which changes timing, not values).

| | Turn 2 | Traced tokens | SSD against RAM | Cold against the SSD |
| --- | ---: | ---: | --- | --- |
| 4B, M4 | 16,479 tokens | 37 | the same first token, tokens and margins, every one bitwise | the same tokens; all 37 margins differ, by up to 0.00629 |
| 9B v2, M2 | 16,530 | 39 | the same first token, tokens and margins, every one bitwise | the same tokens and margins |

Both runs also passed the test's own checks (`trace.log`); their times are those of the instrumented binary.
